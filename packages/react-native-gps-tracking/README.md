# react-native-gps-tracking

Own GPS tracking engine for React Native, built as a [Nitro module](https://nitro.margelo.com): native code collects
raw fixes and step readings and keeps them on disk (iOS: CoreLocation + CMPedometer; Android: Fused Location + `TYPE_STEP_COUNTER` inside a
foreground service). A deterministic distance engine, written once in Kotlin Multiplatform (`tracking-core`) and
running natively on both platforms, decides what counts as distance. JavaScript sends commands and shows snapshots.

**Status: 0.0.1-beta.1. Not built into an app or tested on a physical device.** Every threshold in `TrackingConfig`
is a starting value chosen by reasoning, not measured. Read `doc/FLOW.md` before changing the engine and
`doc/NATIVE_RULES.md` before touching `android/` or `ios/`.

## Install

```sh
bun add react-native-gps-tracking react-native-nitro-modules
cd ios && pod install
```

The iOS pod vendors `ios/Frameworks/TrackingCore.xcframework`, which is built from the Kotlin core and is not
committed: run `bun run build:core` (from this package) before `pod install` when working from the repository.

### iOS

- `Info.plist`: `NSLocationWhenInUseUsageDescription`, `NSMotionUsageDescription` (steps), and
  `UIBackgroundModes` → `location` (recording in the background; without it the SDK reports `MISSING_BACKGROUND_MODE`
  instead of crashing).
- Optional, to bring a recording back after the system relaunched the process, call before the RN host starts
  (`AppDelegate`): Swift `GpsTrackingRuntime.bootstrapAtLaunch()`, Objective-C `[GpsTrackingBootstrap bootstrapAtLaunch]`.

### Android

The library manifest declares the location, foreground-service, notification and activity-recognition permissions and
the `TrackingService` (foreground service of type `location`). The module asks for the runtime permissions itself
(`requestPermission`, `requestStepsPermission`); the host activity must be a `ReactActivity`.

## Use

```ts
import { GpsTracking, trackingConfigForSport } from 'react-native-gps-tracking'

const gps = new GpsTracking() // ONE instance: the native session is global

if ((await gps.requestPermission()) !== 'granted') return

// Bring back a recording that survived a process death, if any.
const recovered = await gps.attachOrRecover({ accept: (id) => id.startsWith('my-') })

const session = recovered ?? gps.createSession({
  config: trackingConfigForSport('running'),
  stepsEnabled: true,
})
const off = session.subscribe((s) => console.log(s.state, s.totalMeters, s.activeTimeMs))
if (!recovered) await session.start({ sessionId: 'my-run-1' })

await session.pause()
await session.resume()
const final = await session.finish() // final only after the journal is durable
const route = await session.persistedFixes()
await session.clearPersisted() // after the activity was saved
await session.dispose()
```

Errors: native failures reject with `TrackingError` (`error.code` is `START_FAILED`, `FOREGROUND_START_FAILED`,
`STORE_WRITE_FAILED`, ...); a call that is not allowed in the current state throws `TrackingStateError`.

### Presenter (Live Activity, ongoing notification)

The SDK depends on no such library. Give `createSession({ presenter })` an object with `onStart`, `onUpdate`,
`onPause`, `onResume`, `onFinish`; calls are ordered, updates are coalesced, each call has a time limit, and a
failing presenter never affects the recording. Android always runs the SDK's own foreground notification;
`session.updateNotification({ title, text })` changes its text.

### External cadence sensor

The SDK never scans or pairs. The host connects to a BLE sensor and reports it:
`session.setExternalCadenceConnected`, `session.pushCscMeasurement(bytes, { sourceId, connectionId })`,
`session.pushExternalCadence(rpm, ...)`.

## API conventions

- Durations and times are milliseconds (`movingTimeMs`, `maxFixAgeMs`, `updateIntervalMs`, ...); a missing value is `undefined`.
- `session.subscribe(listener)` and `session.onFix(listener)` return a function that stops listening. Natively there is
  one fix listener and one snapshot listener; the JS layer fans them out.
- Configuration: `createTrackingConfig({...})`, `trackingConfigForSport(sport)`.
- Native failures reject with `TrackingError` whose `code` is parsed from the native `CODE: message`.
- The distance algorithms exist once, in `tracking-core`; there is no JavaScript copy of the engine.
- iOS relaunch hook: `GpsTrackingRuntime.bootstrapAtLaunch()` (Swift) / `GpsTrackingBootstrap` (Objective-C).

## Layout

```
src/specs/GpsTracking.nitro.ts   the native contract (edit, then `bun run codegen`)
src/{api,domain,platform}        public TypeScript API
nitrogen/generated               generated by nitrogen: never edit
android/                         Kotlin engine + HybridGpsTracking, foreground service
ios/                             Swift engine + HybridGpsTracking
tracking-core/                   shared Kotlin Multiplatform core (+ tests)
doc/                             FLOW, JOURNAL, KMP, NATIVE_RULES
```
